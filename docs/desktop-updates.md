## 客户使用

1. 安装原 1.00 基础包，从网页版“帮助 → 软件下载”获取对应平台的自动更新工具。
2. 保存并正常关闭原软件，运行自动更新工具，在窗口确认原软件位置并点击“接入更新”。Windows 接续原开始菜单和桌面快捷方式；Mac 选择已安装的原 `.app`，由组件保留原程序并接续同位置启动入口，不手工拖动覆盖原应用。
3. 此后从原入口启动即可检查更新；联网失败最多等待清单检查的短超时，再打开当前版本。有更新时展示版本及说明，确认后下载、验证、备份、正常退出后切换并重启。
4. 日常程序内“帮助 → 检查更新”可手动检查；原 1.00 在接入前没有这个新增菜单，仍可再次打开接入后的稳定入口检查。

两平台接入组件和应用仍为开发版。发行签名保证补丁与可信发布者一致，不能替代 Windows 代码签名、Apple Developer ID 和公证；沿下载页的系统提示处理，不关闭系统保护，不绕过恶意软件或损坏告警。

已接入客户如需修复更新助手，可重新运行下载页较新的接入组件；确认后仅替换助手，当前程序版本、已接受序号、原基础程序和资料保持。无需重新选择或注册原基础包。Mac 若提示选择更新接入应用，选择刚打开的更新镜像里的 `LJQCAppUpdater.app`，不要选择已安装的主程序；组件仍须通过完整文件和签名核对。

更新助手显式使用随包的 certifi Mozilla CA，保留证书、主机名校验及 TLS 1.2 最低版本，不依赖客户电脑是否另装Python证书，也不通过环境变量替换可信根。Mac 完整助手清单在最终签名后生成，放在 `.app` 外侧；Windows 清单放在助手目录内。较新合法版本/构建沿用这套工厂和人工修复流程，只有公开02保留精确来源的旧清单例外。

现行0802助手只提供在线更新；程序内手动“检查更新”同样需要联网。网页提供的39/50MB左右工具用于启用或修复自动更新，安装后仍需联网获取程序补丁，并不是完整离线更新包。

## 程序、资料及失败恢复

`desktop_updates` 是独立更新组件，固定资料根为既有 `%LOCALAPPDATA%/LJQCApp` 或 `~/Library/Application Support/LJQCApp`，自选数据库指针继续生效。原基础程序保持可追溯；累计程序归档展开至资料根的 `updates/versions/<build>-<digest>/`，用状态文件切换当前程序。完整程序归档可能接近安装包大小，当前没有小体积二进制差量。

接入先按内置固定清单验证原 06 的全部程序文件；Mac 同目录保留原应用，接入有独立持久日志。更新不初始化在用库，先取得桌面、服务和维护锁及 SQLite 写入保留，生成完整数据库和登记附件的私有备份，在隔离副本初始化新版结构并检查本机服务，最后逐表核对原字段的每个有类型单元格、报告 BLOB 和附件原字节。

首版只接受格式 1 中保持全部原记录的新增表、列等迁移；删除或改写原资料、未知格式、需要搬动附件文件的升级会停止自动安装。已有副本的预检只暂停重复内置目录刷新，仍执行全部结构迁移；正常启动的参考目录准备行为不变，不为通过测试忽略客户记录差异。

需要更新数据库时，新副本先准备在实际数据文件同目录，沿用原文件权限，记录原文件、候选及程序状态后再切换。断电恢复先重验签名、完整程序、资料位置和附件，完成前向切换；资料出现未知新写入时保留当前内容并停止自动处理。已经提交并可能产生新记录的版本永不自动恢复旧库。备份、候选资料、日志和私钥不放公开下载目录。

## 构建和发布

日常入口是 GitHub Actions 的 **Desktop cumulative updates**。已有 **Base installers (explicit only)** 手动入口在未勾选 `rebuild_base_installers` 时也调用补丁构建，可用于在开发分支验收。Windows x64、Mac arm64 必须同源且均通过：

- 隔离源码和资料保护检查。
- 完整程序归档的字节、文件、权限、内链及元数据核对。
- 真正冻结服务的隔离预检、健康和正常退出。
- 真正冻结接入组件的配置自检及 Qt 检查、下载、应用、退出全链探针；实际使用包内CA读取官方签名索引和两平台不可变清单，并拒绝有效期/SAN正确但未受信的自签证书，不能以连接失败代替证书拒绝。
- 实际原02冻结组件无窗口接入，再用新冻结组件修复，保持state/bootstrap原字节、当前程序和最高序号；对修复后的稳定助手再次执行真实HTTPS探针。
- 仅在 GitHub 一次性环境真实安装原06，原冻结程序的本地会话创建旧资料结构；加入隔离测试项目、原报告和附件后，经真实接入及更新器应用本轮补丁，核对全部原资料保持。Windows 的临时安装登记和 Known Folder 路径最后恢复，此检查不冒充 Windows 10/11 客户桌面 GUI 验收。

日常工作流不生成替换基础 Setup/DMG；Windows 的一次性接入 Setup 和 Mac 接入 DMG 使用独立名称。GitHub Artifacts 是中间成品，客户下载始终来自自有 HTTPS。

签名清单使用内置 Ed25519 公钥。发布在两平台完整成功后进行，校验版本、共同源码、原生回执、长度和 SHA-256，再通过专用身份上传。服务器复核并实际通过 HTTPS 下载核对新文件，最后原子切换一个双平台渠道索引；不把逐个改写多个 `latest.json` 当作原子发布。错误发行撤回入口后发布更高构建修复，不自动降级已升级客户。

更新清单有效期 14 天；每周工作流只重签已验收发行的时效及递增序号，程序文件和基础包不重建。部署身份与发行签名身份分开，服务器不持有签名私钥。

### 大文件交付与重发

双端验收、签名完成后，GitHub 保留原始签名附件。日常完整发布默认通过固定 SSH 接收命令直接发送原文件，传输上限18000秒、发布任务上限360分钟；客户端下载地址仍为自有服务器。本轮 GitHub 跨区拉取及直接上传均出现约50–70KB/s慢网，故普通传输预留5小时，任务总限6小时，不能再用原900秒时限发送约740MB发行。GitHub托管任务的[执行时限](https://docs.github.com/en/actions/reference/limits)为6小时；显式任务配置不超过[360分钟](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idtimeout-minutes)。大文件尚未核验完成时，客户端下载页与更新检查继续使用上一已发布版本。

手动明确选择 `raw_transfer=false` 时，也支持只发送四个小型元数据文件，由服务器通过 HTTPS 下载这一份附件。GitHub API 凭据留在 runner，服务器仅收到单附件、短期、只读的下载地址，不获得仓库访问令牌。地址只留在私有暂存，不进入日志、回执、公开清单或网页；进程被强行终止或主机断电后可能保留私有暂存，须核对来源后清理，不能移到公开目录。

接收端先检查原签名、双平台来源和频道反回放，再校验明确允许的官方存储主机、路径及每次重定向，按长度和 SHA-256 下载 ZIP。它只接受签名清单列出的完整文件集，重验原索引和平台清单的原始字节，最后沿既有发布锁核验并切换频道。失败保留上一频道；每周三个小清单仍直接传输。官方存储分片变化须单独审核，不自动扩大网络白名单；原始普通 tar 传输保留较长时限作为兼容路径。

如果仅传输失败，使用 **Resend an accepted signed desktop update** 手动入口，选择 `main` 并明确勾选 `publish`，填写原运行号、尝试号、签名附件 ID/SHA、源码提交/摘要、版本和构建号。保持默认 `raw_transfer=true` 即直接重发原文件；明确设为false才尝试小引用交付，不做自动SSH重试。该入口只读取两个部署 Secrets，不取签名私钥，不构建或重新签发清单；它要求 GitHub API 确认原 main 同源双平台全部原生步骤及签名保留成功，原失败只能是受限传输步骤。附件已过期、来源不符或验签失败应停止。清单确已过期时需另走已验收发行的元数据刷新，不用重发绕过有效期。

0802 原程序来源固定 `dc4af0e84aac02a120294e19469c2d5bef96976c`、摘要 `90bc8c66b1978e7bb71fb1321d759cf910eec3ab7bcebd708dab8e2ca8ecd4af`；后续仅交付控制变更不改变这两项，也不重新导出网页部署使用的 68123 字节源码 bundle。实际发布结果见交付回执，代码具备重发能力不代表已经晋级频道。

## 配置边界

GitHub 环境 `desktop-updates` 使用：

| 名称 | 用途 |
| --- | --- |
| secret `LJQC_UPDATE_SIGNING_KEY` | 专用 Ed25519 原始 32 字节私钥的 Base64，只用于可信发布任务。 |
| secret `LJQC_UPDATE_DEPLOY_KEY` | 专用上传身份，不使用个人或 root 通用密钥。 |
| secret `LJQC_UPDATE_KNOWN_HOSTS` | 从可信控制台核对的固定服务器主机公钥，禁止忽略主机验证。 |
| var `LJQC_UPDATE_DEPLOY_USER` | 仅可接收补丁的服务器账号。 |
| var `LJQC_UPDATE_DEPLOY_HOST` | 默认 `159.75.243.120`。 |
| var `LJQC_UPDATES_AUTO_PUBLISH` | 明确设为 `true` 后允许 main 的成功构建自动晋级。 |

缺少配置时工作流明确报告候选或签名成品状态，不能宣称已经发布。开发分支不自动发布；部署身份不能读取业务目录、执行任意 shell 或改业务 systemd。环境限制及分支规则应与发布身份一起配置。GitHub Secret 的使用方式见[官方文档](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)。

公开 `/updates/desktop/dev/<target>/latest.json` 由原子渠道索引解析；网页从服务器本地 `updates/desktop/dev/current/release-index.json` 读取已签名的接入组件记录，未发布或校验失败时仅禁用接入按钮。现有 `/downloads/releases/1.0.0/2026110606/` 原文件继续固定。
