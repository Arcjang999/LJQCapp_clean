# 逐卡执行规则

版本：2026-09-22。本文是开发约束，不能显示到软件界面。用户要求把剩余任务拆细，本轮仅交付任务书；文档完成不代表功能完成。

## 1. 每次只领取一张卡

1. 读 `AGENTS.md` 的当前口径、[执行总表](README.md)、本规则、用户指定卡及卡中列出的文件。历史规格仅用于查证，不从旧文档的“下一步”领取额外任务。
2. 检查工作区，保留已有修改；核对卡的前置状态和对应交付记录。卡里列出的函数是 2026-09-22 的定位线索，若上游后续改变名称，沿上游接口合同定位，不复制旧实现。
3. 开始前用不超过五句话说明：本卡结果、现有可复用能力、计划改动文件、验收方式、明确停止点。随后执行，不停在计划。
4. 实现卡只完成本卡的增量；相邻模块仅允许为满足本卡明确接口作必要接线。若必须新增业务规则、重写算法或跨卡大改，记录具体差异和受阻分支；继续独立可做的部分，不用猜测填空。
5. 按验收场景留证据，再回填[进度表](STATUS.md)和本卡交付记录。完成后停止，不自动进入下一张卡。用户明确指定连续多卡时才按前置顺序继续。

“一次一张卡”限制任务范围，不要求每卡都向用户重复申请开发许可。字段命名、局部代码组织、附件大小等技术选择可在卡允许范围内自行落实；真正待确认的业务规则见[决策清单](DECISIONS.md)。

## 2. 要求与建议的优先级

用户最新明确要求 → 原任务书及会议记录中的已确认需求 → 本轮执行卡中的落实细节 → 旧实现说明和参考手册。

- **已确认需求**不能因卡拆细而丢失。卡与原文矛盾时，修正卡并说明，不能悄悄削减交付。
- **工程默认**用于减少反复设计，不是新增临床规则。例如任务 2 首版选择全组原子保存，原任务明确允许。
- **待确认业务规则**不能自动变成默认值。决策卡交付“准确的问题、现状证据、有限选项及影响”，收到明确答案后才将对应规则标为确定；建议答案不算用户确认。
- 不因目标 Windows 或真实系统缩放环境暂缺，停止本机可进行的开发。环境未验收的发布项保持待验收，不宣称全部发布通过。

## 3. 当前基线，不重复开发

任务 0、统一业务模糊搜索及本轮标准复核已有实现，详情见 [复核记录](../task_00_reaudit_2026_09_22.md)。项目中心、现有管理弹窗、质控品/参数/试剂生命周期和试剂使用事件更正也已有实现。

- 不重新做任务 0，不以凑目录条数为目标；质量要求目录只出现现行依据。历史记录已采用版本的追溯保留。
- 所有新增搜索复用 `services/search_service.py`，搜索只找候选。产品覆盖关系、具体批次、标准适用性、权限和记录关联使用稳定标识与明确校验，不能模糊推断。
- 复用 `quality_review_service` / `quality_applicability_service` / `quality_identity_service` 的统一准入；项目批量带入、导入、复制及换批不另写宽松规则。无适用数值要求不等于没有适用过程要求。
- 实验室资料复用系统设置，不新增第二份实验室信息页面。临时质控不是即时法。已有试剂使用事件更正不是具体检测记录的历史批号更正。
- 旧测试数据不是适配约束，不专门做旧演示库迁移，不主动清空用户库。新增功能运行后的原始记录、报告、附件和后续备份必须可追溯；不以“不要旧数据”为由破坏新功能的数据完整性。

## 4. 永久业务与界面约束

1. 开发语言、代码、内部字段、开发注释、异常堆栈、测试说明和实现状态不能出现在任何业务页面、帮助、弹窗或提示中。日志和开发文档可以保留技术细节。PDF/CSV 等必要文件类型可显示。
2. 中文业务用语沿现有词汇表；保存、取消、离开时草稿行为明确。Enter 不自动提交管理弹窗；记录录入中的 Enter/Tab 行为按对应卡测试。
3. 一个项目可含不同质控方法、方法学和输入类型；单一检测项的类型须明确。多水平法按完整 run 保存及判定，各水平不是独立整次结论。
4. 不更改 `qc_logic.py`、`zscore_logic.py`、`services/instant_service.py`、`services/outlier_service.py` 中的公式、规则阈值、判定粒度，以及两个绘图文件的现有计算含义。优先在调用侧加适配；确需接入改动时列出最小差异及等价证据，不能借“接入”重写算法。
5. 警告、失控、处理中、处理完成是不同维度；后续在控不自动结束失控事件。换批不改旧检测，复测新增记录，不用更正掩盖真实异常。
6. 不顺带开发 LIS、联网许可、多租户、电子签名、即时法月报、通用性能验证平台、未确定的长期/加权 CV 或新临床规则。

## 5. 数据、接口与失败要求

- 页面负责交互，关系校验/业务保存/计算协调在服务层。新接口在本卡交付记录写清输入、输出、稳定标识、错误、事务和版本约束，下一卡消费已验收合同。
- 新表或字段只是候选设计；优先复用能满足含义的现有对象，不为每张卡另造一个同义模型。
- 复用现有 `database.atomic_write` 时验证下游未独立提交；不能把逐个成功提交伪装成全组原子提交。文件和数据库的协调失败也要检查，不能只断言页面提示。
- 对保存失败、重复点击、陈旧窗口、取消与再次进入，按本卡范围给出确定行为。重试不能生成重复有效记录或不必要的报告历史。
- 任务 5 的开发卡可分别完成，但任何用户可写的维护入口必须等 T5-12 全链验收才开放。修改、补录、排除/恢复与重算必须一起成功；不能发布“先改数据、稍后手工重算”。

## 6. 验收与证据

每卡验收包括卡内的正常、失败与边界案例。数字示例仅为隔离工程测试，不是临床接受标准。以现有算法作为结果对照时，要独立准备输入并检查关键输出；不能只用同一新函数计算两次证明正确。

实施证据建议放 `output/execution/<卡号>/<运行日期>/`，不要提交数据库、患者资料或本地二进制。可读交付记录放 `docs/execution/deliveries/<卡号>.md`，至少写：

| 内容 | 必须记录 |
|---|---|
| 范围 | 卡号、实际修改、未做事项；不是复制需求清单 |
| 接口 | 新增或改变的输入/输出/事务/版本约束；无变化写无 |
| 验证 | 环境、测试命令或实际操作、预期与实际、证据位置 |
| 数据 | 隔离库位置、失败回滚/备份等本卡相关结果 |
| 结论 | 通过/部分完成/待业务决策/待环境；不得把未运行写通过 |
| 下一步 | 下一张允许执行的卡及仍阻塞的具体分支 |

服务测试不能替代浏览器交互验收；PDF 不能只检查“文件存在”，报告卡需要逐页渲染验证。系统缩放必须记录真实设备设置，缩小视口不算 200% 系统缩放。

只运行与本卡相关且必要的验证；阶段验收卡再走对应完整链路。已通过且未受本卡影响的全量测试不反复跑。文档卡检查来源、链接、逻辑与覆盖，不启动应用或迁移数据库。

## 7. 统一状态

卡的静态头部保留拆分时状态；动态状态以 `STATUS.md` 为准：未开始 → 进行中 → 已完成，或待业务决策 / 待资料 / 待环境 / 部分完成。回填状态必须有交付记录链接。

“阶段已完成”须末尾验收卡通过；未决分支存在时可记录其他卡通过，不能把全阶段涂成已完成。本轮创建了执行卡，所有功能卡仍未开始。
