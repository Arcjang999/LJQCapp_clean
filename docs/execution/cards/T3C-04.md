- 原需求锚点：[原任务 3C](../../task_03_comparisons_and_monthly_reports.md#4-3c批量月报与汇总)；[合并需求](../../requirements_merged_2026_09_21.md) §4.5—4.6。

执行前阅读 [统一执行规则](../EXECUTION_RULES.md)。本卡是待执行范围，不表示功能已经实现。

## 1. 目标及用户可见结果

- 一次下载已成功报告，文件名能识别项目、批号与月份，同名项目也不覆盖。
- 从批量结果进入每份独立报告历史，失败项仍可查并重试。

## 2. 必读实际文件与复用函数

- `pages/report_history_page.py::render_report_history_page / _render_report_history_card`：单份历史。
- `services/report_service.py::get_report_history_record / filter_report_history_records`：精确读取与查询。
- `services/report_service.py::_build_report_file_name / _build_zscore_report_file_name`：现有文件命名，补批量碰撞处理。
- 任务 1 文件存储与 T3C-03 成功条目；拟新增归档生成和清单输出，不另存一份合并月报。
- 所有业务搜索复用 `services/search_service.py::fuzzy_match / filter_frame`；选中后以稳定身份精确关联。

## 3. 逐步实施、数据关系与失败行为

1. 从成功条目获取已保存报告文件及历史引用，下载归档只读已有产物，不触发新报告生成。
2. 设计业务可识别文件名，含项目、实际批号、月份和必要仪器/序号消歧；禁止目录穿越或覆盖。
3. 归档附清单，列出成功文件与失败/排除项目及原因，不让用户误以为选中全部已生成。
4. 批量结果提供单份下载和报告历史入口，筛选使用模糊查找，点击仍精确定位历史。
5. 归档失败只提示下载准备失败，已成功报告和历史保留，可重新生成归档或逐份下载。
6. 核对 ZIP 解包后每份 PDF 可打开，恢复/迁移后再次下载与原保存版本一致。

数据契约与状态：

- ZIP 是已有单份文件的集合，不是新的临床报告，不新增月报统计。
- 文件名碰撞按稳定条目消歧，不能用覆盖解决；清单保留文件与报告身份的对应。
- 下载失败与报告生成失败分别展示，重下 ZIP 不改变历史数量。

## 4. 本卡不做与禁止事项

- 不把成功与失败混写成“全部完成”，不隐藏失败清单。
- 不以点击下载为由重新计算当前数据覆盖旧报告；不合并不同批号 PDF 内容。
- 不修改既有质控公式、规则阈值或 Z-score 整次检测判定粒度；任务 0 的适用性继续精确判断。
- 界面不得显示编程语言、代码、开发说明、内部字段或错误堆栈；使用实验室业务用语。

## 5. Given–When–Then 验收

1. Given 两仪器有同名项目和批号；When 下载 ZIP；Then 文件均保留且可区分，无互相覆盖。

2. Given 部分报告失败；When 下载成功部分；Then 归档清单标明失败项，成功 PDF 都可打开。

3. Given ZIP 准备失败；When 再次下载；Then 原报告历史数量不变，可继续逐份下载。

4. Given 用户从批量清单打开一份历史；When 查询详情；Then 指向其原版本、批次和月份，不跳到最新同名报告。

## 6. 证据与完成条件

- 归档清单、解包文件数量及所有 PDF 打开/逐页核对结果。
- 重下/失败重试的历史数量和文件内容一致性，常规/高缩放页面可读性证据。
- 证据逐条对应本卡验收编号，记录未执行项和失败原因；未通过不得勾选完成。
- 执行实现或验收时仅使用独立库/明确副本，记录版本和保护范围；此次编写卡片不运行应用或数据库操作。
