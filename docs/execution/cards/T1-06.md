# T1-06｜人工确认处理效果并保留完成后修订

- 原任务：任务1《失控原因分析、复测关联、附件与独立报告》
- 状态：未开始
- 类型：实现
- 前置卡：[T1-05](T1-05.md)
- 本卡交付：状态转换、确认校验和完成后新版本
- 原需求锚点：[任务1](../../task_01_out_of_control_reports.md)第2节“处理状态”、第3节；[需求合并稿](../../requirements_merged_2026_09_21.md)第4.3节
- 执行公约：[EXECUTION_RULES.md](../EXECUTION_RULES.md)，执行前必须遵守。

## 1. 目标及用户可见结果

用户区分处理中、待确认与已完成，能够看到是谁何时依据什么完成。
完成只是处理结论；原检测仍保留失控或警告判读。

## 2. 必读实际文件与复用函数

- T1事件服务和`ui/out_of_control.py`：沿既有事务与版本机制扩展，不另建独立状态字段。
- `ui/traceability.py`：业务时间与原判读展示；`services/lot_lifecycle_service.py`判读版本只读引用。
- `database.py`：`atomic_write`；处理版本与状态历史同事务。
- 拟新增`tests/out_of_control_completion_smoke_test.py`及状态转移矩阵测试。

## 3. 逐步实施

1. 实现待确认提交：按T1-01确认矩阵校验原因、措施、处理人和效果资料，缺项列出具体业务名称。
2. 确认前再次加载当前事件版本和复测证据；展示原异常、关联复测、差异说明、患者影响评估及未记录项。
3. 完成动作必须明确填写确认人、确认时间与效果说明，并明确确认；空白或非法时间不能用默认姓名悄悄填充。
4. 未复测或仍需调查可保存处理中；不得因为后续在控、填写“已处理”或导出PDF自动完成。
5. 待确认退回处理中须理由；已完成修改原因、措施或关联复测时要求修订原因，新增版本并重新进入需确认状态。
6. 保存完成与修订历史时校验期望版本；陈旧确认不能覆盖新资料，失败保持当前持久状态并保留未提交输入。
7. 已出报告绑定旧完成版本；修改处理中资料不回写旧PDF，详情明确显示已归档版本与当前状态。
8. 处理人和确认人均只作记录；不添加必须不同人的审批规则，也不冒充账户认证或电子签名。

## 4. 本卡不做／禁止

- 不修改原结果数值、规则、参数或在控/失控结论。
- 不自动结束无复测事件，不推断患者结果放行。
- 不在本任务引入管理员账户规则或多级审批。

## 5. Given–When–Then 验收

1. Given：原因、措施、效果、人员和复测齐全。
   When：先提交待确认，再人工确认。
   Then：状态已完成，历史含两次动作且原失控结论不变。

2. Given：原因分析为空或确认人全为空格。
   When：确认完成。
   Then：列出缺项，状态不变且无完成版本。

3. Given：事件处理中但后续新增在控复测。
   When：刷新事件。
   Then：仍处理中，必须显式关联和人工确认。

4. Given：完成V3且已导出报告，现需补充措施。
   When：填写修订原因保存V4。
   Then：V3及旧报告可读，V4重新核对，不能静默覆盖。

## 6. 需要留下的证据与完成条件

- 按四状态列出允许/拒绝转换测试和业务提示。
- 确认/退回/修订全链浏览器记录、并发旧版本拒绝证据。
- 来源数值和判读前后对照一致，旧完成版本内容可回读。
- 未执行或未通过的项标注具体缺口，不用“代码已写”代替本卡验收。
