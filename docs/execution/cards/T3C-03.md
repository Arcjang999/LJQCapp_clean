# T3C-03｜逐份生成状态与失败重试

- 本卡交付：批量任务及每份报告独立状态、成功历史、失败原因和定向重试。
- 原需求锚点：[原任务 3C](../../task_03_comparisons_and_monthly_reports.md#4-3c批量月报与汇总)；[合并需求](../../requirements_merged_2026_09_21.md) §4.5—4.6。

执行前阅读 [统一执行规则](../EXECUTION_RULES.md)。本卡是待执行范围，不表示功能已经实现。

## 1. 目标及用户可见结果

- 看到每份报告正在生成、成功或失败；一份失败时已成功报告仍保留。
- 只重试失败或明确选择的报告，不无提示重新创建全部历史。

## 2. 必读实际文件与复用函数

- T3C-01 清单合同与 T3C-02 共同单份生成接口。
- `database.py::atomic_write / create_report_export_snapshot`：每份历史写入边界。
- `services/report_service.py::save_lj_monthly_report_snapshot / save_zscore_monthly_report_snapshot`：已存在历史保存。
- 拟新增批量任务/条目存储和执行编排；任务状态为实现建议，界面使用普通业务表述。
- 所有业务搜索复用 `services/search_service.py::fuzzy_match / filter_frame`；选中后以稳定身份精确关联。

## 3. 逐步实施、数据关系与失败行为

1. 将用户确认的清单保存为任务及独立条目，保留方法/批次/月/源版本/请求身份与排除项。
2. 逐条调用共用生成器，条目至少区分待生成、处理中、成功、失败；成功关联一份明确历史及文件。
3. 以每份为事务边界保存成功结果，单份失败记录可读原因后继续其他项，不回滚已经成功的报告。
4. 中断后可识别未完成项，重新检查是否已有对应成功历史，避免重启或重复点击生成重复记录。
5. 提供只重试失败/未完成项的操作，成功项默认跳过；主动重新生成须明确形成新版本。
6. 失败重试重新检查源版本，源已变化须说明重新预览而非悄悄沿用旧请求混合数据。

数据契约与状态：

- 条目成功必须同时具有有效 PDF 与历史引用；任务整体成功不能掩盖未完成条目。
- 稳定请求标识用于重复提交去重；有意新报告版本与同次重试是不同操作。
- 错误技术细节进日志；页面保留失败项目、业务原因和可操作的重试状态。

## 4. 本卡不做与禁止事项

- 不因一份失败清空成功清单，也不重试时无提示重建全部历史。
- 不通过给失败文件空字节标记成功，不把一批任务包装成一个共同报告历史。
- 不修改既有质控公式、规则阈值或 Z-score 整次检测判定粒度；任务 0 的适用性继续精确判断。
- 界面不得显示编程语言、代码、开发说明、内部字段或错误堆栈；使用实验室业务用语。

## 5. Given–When–Then 验收

1. Given 3 份报告其中第 2 份失败；When 任务结束；Then 第 1/3 份独立成功且有历史，第 2 份有失败原因。

2. Given 上述任务；When 仅重试失败项；Then 原成功历史不增加，只处理第 2 份。

3. Given PDF 已成功但界面响应中断；When 恢复同一请求；Then 检查已有成功引用，不重复生成全部报告。

4. Given 重试前源数据已改变；When 重试；Then 提示重新核对该项数据版本，不能静默混用旧预览。

## 6. 证据与完成条件

- 单份失败注入、中断恢复、重复点击、版本变化及成功历史数量对照。
- 浏览器任务进度与重试路径，验证业务错误可理解且不泄露堆栈。
- 证据逐条对应本卡验收编号，记录未执行项和失败原因；未通过不得勾选完成。
- 执行实现或验收时仅使用独立库/明确副本，记录版本和保护范围；此次编写卡片不运行应用或数据库操作。
