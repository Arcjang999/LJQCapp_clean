日期：2026-11-06。状态：稳定桌面资料、最小兼容防线、首次方法选择与教程、两平台构建配方已本地实现；Mac 待签名 DMG 已生成，Windows 源码构建资料已导出、Setup 待原生执行。完整升级协调/自动在线更新和统一发布仍待实施。实际范围见[首轮安装包交付](deliveries/DESKTOP_INSTALLERS_2026-11-06.md)。

本轮确定 Windows 10/11 与 macOS 分别发行，桌面启动时检查服务器版本，网页与桌面采用同一轮正式版本发布。建议先建立独立数据目录、安装包和完整程序包升级，再接在线更新与统一发布。首版更新完整程序；差量补丁在发行结构稳定后加入。

Windows 10/11 共用一份 x64 安装包。用户已确定 Mac 仅支持 Apple 芯片（M 系列），使用 arm64 安装包。两个平台分别构建和验证。检测记录、报告和附件继续按网页端或本机原有保存位置管理，版本服务负责分发程序。

安装包使用空白业务库，用户已取消 HIV RNA 演示项目，所有客户项目及实际资料由客户设置。空库首次进入时先选择单水平或多水平，再按所选方法完成首次设置；第一次进入对应工作台时显示简短教程。

## 2 用户安装和更新体验

客户从“帮助 → 软件下载”进入下载页，分别选择“Windows 10/11 64位”或“Mac Apple 芯片”。Mac 页面说明可在“关于本机”查看芯片信息。安装后由客户端根据自身构建目标选择更新，不能只依靠浏览器识别系统。

| 用户电脑 | 首次安装包 | 后续更新目标 |
| --- | --- | --- |
| Windows 10/11 64位 | `LJQCApp-Setup-<version>-windows-x64.exe` | `windows-x86_64` |
| Mac Apple 芯片 | `LJQCApp-<version>-macos-arm64.dmg` | `macos-arm64` |

开发改造方案保存在本文件 `docs/execution/DESKTOP_UPDATE_AND_RELEASE_PLAN_2026-11-06.md`，通过项目交接文档和 `AGENTS.md` 索引。客户下载页只呈现平台、正式版本、发布日期、包大小和下载入口。

当前尚无这两种正式安装包。页面为未发布平台显示“安装包准备中”，不提供占位或旧试用包链接。新增 `resources/software_downloads.json` 保存经发布流程核对的安装包展示信息；`services/software_download_service.py` 校验各平台记录，`ui/software_downloads.py` 展示，主路由和帮助菜单提供入口。清单缺失或损坏时仍能返回主页；单个平台坏记录不隐藏另一平台的有效发布记录。

该展示清单用于呈现正式下载地址，在线更新器仍须实现第二轮的签名及版本校验。真正的安装包继续放服务器独立发行目录；产品页面、发行程序和客户业务资料分别管理。

### 空库首次设置与新手教程

正式安装包首次使用时没有预置项目、批次、检测结果或报告，也不预填客户的实验室名称、人员、仪器、试剂批号、质控品批号及靶值。内置的标准、单位及产品目录继续作为客户选用的参考资料，不能代替客户的实际登记和确认。已有本机或云端资料继续保留，空库要求只适用于全新使用。

首次流程为：

`打开空白业务库 → 选择单水平或多水平 → 登记本单位实际资料 → 建立首个检验项目和批次 → 对应工作台显示简短教程`

方法选择不给默认项，使用两个简短选项：

| 选项 | 用途说明 | 后续引导 |
| --- | --- | --- |
| 单水平（L-J） | 每次录入一个水平的质控结果。 | 设置一个水平，按客户选择的建靶或已确认参数方式完成首个检验项目。 |
| 多水平法 | 每次一起录入多个水平的质控结果。 | 选择实际水平数，为各水平选择产品、原厂批号和参数，再建立首个检验项目。 |

此选择只决定本次教程与首个检验项目的草稿预填。客户可在保存前调整，后续也可使用另一方法；项目内各检验项目仍可分别选择方法。选择教程本身不创建项目、不保存批次、不代替质量核对或参数确认。即时法仍沿现有单水平入口按需选择，首次选择页只呈现用户要求的单水平和多水平两个选项。

资料准备复用已有“实验室信息 → 仪器试剂管理 → 新建项目”入口及保存校验，并根据所选方法带入首项草稿。必需资料由客户填写；缺项时提示对应字段和处理入口。提示只写当前要做的事，每处以一句为主，教程保持简短。

第一次进入对应工作台时，可使用以下教程提纲，并以实际按钮名称校对最终文案：

| 方法 | 简短教程提纲 |
| --- | --- |
| 单水平（L-J） | 核对当前项目和批号；填写检测时间、检测人和一个质控值并保存；查看质控图和判读，需要时生成报告。 |
| 多水平法 | 核对各水平产品和批号；同一次检测填写全部水平结果并保存；查看整次检测判读和各水平质控图，需要时生成报告。 |

复用现有空业务库自动弹出的首次引导，增加方法选择和按方法带入草稿。引导进度绑定数据库，保留“稍后再做”、继续和手动入口。教程按数据库及方法分别保存已查看状态，查看单水平教程不会同时标记多水平教程；正常升级保留这些状态。已有业务库升级时沿用不强行启动首次设置的约定，客户可从帮助手动查看教程。

旧引导的步骤、跳过和完成状态继续有效；接续旧的未完成进度时保留原步骤，在需要按方法建立项目时再补选方法。现有引导状态只规范化 `version/step/status`，方法选择和各方法教程状态使用独立设置键保存，避免扩展字段被旧规范化函数丢弃。切换数据库后使用该库自己的引导状态，不用安装次数、版本号或教程状态缺失代替首次使用判断。教程以最终保存并实际进入的工作台方法为准，不能一直沿用最初选择。

现有 `services/demo_data_service.py` 的旧 full/basic 示例及“写入演示数据.bat”不会用于新的客户发行包；首次启动、覆盖安装和更新均不能向客户库写入旧示例或恢复仓库试用快照。此处沿用用户最新的空库引导要求，不实施此前讨论的 HIV RNA 示例或独立演示入口。

已发出的旧桌面包需要先安装一次带更新器的新发行版。首次接入核对原保存位置；后续检查和更新由启动器完成。

每次启动先读取已验证、已下载的待安装版本；满足安装条件时，在业务页面打开前完成升级。网络检查采用短超时，只取小型版本信息；无新版时直接运行。建议提供“立即更新”和“稍后”，也可在使用期间后台下载，下载完成后在下一次启动前安装。进入录入后继续运行当前版本，设置中的“检查更新”只负责检查和下载。

断网、版本服务超时或元数据过期时，继续使用本机已安装且与当前数据兼容的版本。损坏的包、错误系统或架构、签名无效、磁盘不足均取消本次升级。客户端不自动绕过系统安装保护。

## 3 程序与资料分别保存

| 平台 | 程序位置建议 | 固定配置及默认资料位置 |
| --- | --- | --- |
| Windows | `%LOCALAPPDATA%\Programs\LJQCApp\`，包含稳定启动器、更新助手及 `versions\<build>\` | `%LOCALAPPDATA%\LJQCApp\`，分别存放 `config`、`data`、`backups`、`updates`、`logs` |
| Mac | `/Applications/LJQCApp.app` 或 `~/Applications/LJQCApp.app` | `~/Library/Application Support/LJQCApp/`；日志可放 `~/Library/Logs/LJQCApp/` |
| 网页服务器 | 程序继续使用 `/opt/ljqcapp` | 继续使用 `/var/lib/ljqc`，沿用服务器现有数据库、附件和备份 |

用户已通过系统设置选择的数据库位置继续生效，附件仍跟随实际数据库路径。安装、程序升级和普通卸载保留固定资料目录及自选位置。独立数据目录是默认设计，不增加实验室账号或多租户。

首次接入按确定的旧软件文件夹定位原配置，避免从多个副本中猜选数据库：

1. 关闭旧窗口、备用浏览器服务及维护进程，取得安装和实际数据库路径对应的锁。
2. 有有效自选路径时，将该指针写入稳定配置，继续使用原库；原库缺失或配置损坏时提示选择原软件文件夹或核对保存位置，保留原资料。
3. 原来使用包内默认库时，把数据库、登记附件和报告一起复制至稳定资料目录，核对后最后写配置。原位置先保留，使用完整快照协调 SQLite 的 WAL 等文件。
4. 配置、候选目录或目标已有资料存在冲突时停止切换，不能静默改用新空库，也不能仅移动一个 `.db` 文件。

## 4 数据兼容和升级失败处理

这是接入自动更新前的必要基础。当前 `projects`、`results` 的部分旧结构判断会把额外列也视为需要重建，并只复制已知字段。因此，即使将来的迁移只是增加列，也不能直接把旧程序连接到新库。

增加明确的数据结构版本、最低兼容程序版本和完整迁移登记，在自动旧库迁移、`init_db()` 及任何业务写连接之前进行只读检查。首次接入只有经识别和验证的基线才能登记为受支持结构；未知结构保留原状并停止自动升级。调整“列不完全相同就重建”的判断，防止把未来结构当成旧格式处理。

切换过程采用持久阶段日志：

`已下载并验证 → 已取得维护锁 → 已封存原资料 → 候选迁移与验证通过 → 程序和资料已切换 → 启动验证通过 → 允许业务写入`

更新器从最终快照到放行写入一直协调维护状态。正常关闭时先结束在途写入、等待连接和 Qt 子进程释放；无法安全退出则延期更新。现有 `taskkill /F` 不作为常规升级动作。单实例和资料锁应覆盖桌面窗口、备用浏览器入口、维护工具及更新器。

先由旧版本生成完整备份，或使用不初始化数据库的原始封存，再让新版在候选库上验证迁移。当前公开备份 API 会调用 `init_db()`，不能先让新版通过“备份”接触在用库。现有完整备份、附件清单、哈希核对和恢复前保护可以复用；多处显式提交与跨文件操作仍需独立的断电恢复设计。

候选库通过完整性、外键、原记录和字段、附件哈希、历史报告字节及业务验证后，才切换正式资料。候选资料在目标文件系统内暂存，配置和程序入口采用可恢复的切换方式；程序、数据库及附件的多文件变化由阶段日志协调。

| 失败时点 | 恢复规则 |
| --- | --- |
| 下载安装前 | 保留现有程序和资料，重试下载。 |
| 候选升级未通过 | 保持原程序和原资料，保留失败日志与候选资料供诊断。 |
| 已切换但尚未允许新业务写入 | 根据阶段日志恢复升级前相互匹配的程序、库、附件及配置，验证后再启动。 |
| 新版已保存新结果、报告或附件 | 保留最新资料；只有经验证兼容时才退回旧程序。不能自动恢复升级前备份覆盖新增资料，应发布修复版或执行经验证的逆向迁移。 |

## 5 平台安装和更新实现

Windows 保留现有 Qt 窗口及本机服务。新增不依赖待替换 Qt 目录的稳定启动器和独立更新助手；下载完整版本到新目录，验证后切换 `current.json`。更新器本身升级需要最低版本约束和独立替换流程。安装器建议采用支持普通用户安装、快捷方式、卸载及程序签名的成熟工具。

Mac 新增 `.app` 构建配方及 DMG 分发。更新时协调主窗口、本机服务和 QtWebEngine 子进程退出，再整体更换应用包并重启，保持包内权限和符号链接。开发阶段先验证 Qt 桌面壳与平台更新助手的接线；可评估 Sparkle 作为安装更新实现，其协议适配和签名验证须以本项目实包验证为准。[Sparkle 官方说明](https://sparkle-project.org/documentation/)

对外 Mac 发行使用 Developer ID 签名、所需 hardened runtime 权限、公证及票据装订，并验证 Gatekeeper 的正常打开体验。更新包签名与 Apple 应用签名分别管理。[Apple 发行说明](https://developer.apple.com/developer-id/)

Mac 构建固定为 arm64，Python、Qt 和全部原生依赖均需具备该架构。最低 macOS 版本在选定依赖并完成目标系统验证后写入清单。[PyInstaller 架构说明](https://pyinstaller.org/en/stable/feature-notes.html#macos-multi-arch-support)

当前配方同时收集源码资源和冻结模块，逐个覆盖 `.py` 可能形成混合版本。第一版替换完整程序目录或整个 `.app`。差量更新以后基于完整构建产物生成，绑定精确起止版本、核对重建后的完整目标包，失败转用整包。

发行包只带程序、内置目录、帮助和必要运行环境。构建检查排除在用数据库、演示数据库或试用快照、保存位置配置、业务附件、备份、日志和签名私钥；客户数据库在首次使用时初始化为空白业务库。解压前验证大小与路径边界，暂存完成后复核完整目标；Mac 应用内必要的符号链接需保持在受验证的包范围内。

## 6 网页和客户端同一轮发布

新增唯一版本源 `release.json`，通过统一读取模块生成网页显示、桌面显示、Windows 文件版本、Mac 构建版本及下载清单。所有端共用正式版本号、递增构建序号和完整 Git 提交，各自记录目标系统与架构。

更新元数据记录：目标、版本、构建号、来源提交、包地址、大小、SHA256、签名、最低系统和更新器版本、数据兼容范围及迁移路径。客户端信任随软件内置的公钥，检查签名、元数据有效期和版本次序；SHA256 仅用于内容校验，不能独立证明来源。密钥轮换需要预先定义信任交接。可复用成熟的更新元数据规则，采用自定义字段时不宣称已经符合完整 TUF。[TUF 元数据说明](https://theupdateframework.io/docs/metadata/)

服务器新增独立静态目录，例如 `/srv/ljqc/releases/<release_id>/<target>/`，只提供经过验证的公开程序和清单；不直接开放源码、在用库、附件或备份目录。域名、HTTPS、下载流量和缓存配置与现有网页代理一起部署。签名私钥保存在受控构建发布环境，下载服务器与客户端仅保存所需公钥。

发布依次完成：

1. 从同一提交构建所需的 Windows 和 Mac 包，完成签名及各平台验收。
2. 上传到不可变版本目录，复核包和签名，保留正式版本入口指向原版本。
3. 网页端预告短暂维护，让使用者保存当前填写内容并退出；维护期间阻止新增业务写入，备份服务器当时资料，部署同一提交。通过服务、真实页面和资料核对后恢复使用。
4. 发布签名后的正式更新元数据，客户端下载新版本；下载页显示同一轮平台包。
5. 保存每一阶段的回执及已发布目标。网页部署失败时不发布客户端入口；网页成功而更新入口发布失败时，按日志补发。

“同一轮发布”表示两端来源和版本一致。网页部署完成后生效，桌面端在各自联网并完成升级后生效。已升级的客户端不受服务器入口退回影响；必要时发布更高构建序号的修复版，并遵守其数据兼容范围。

## 7 分三轮实施和验收

| 轮次 | 交付内容 | 完成条件 |
| --- | --- | --- |
| 第一轮 安装及升级基础 | 固定配置和数据目录，首次旧包接入，空库方法选择与首次设置，按方法的新手教程，统一版本，兼容门槛，单实例与正常退出；Windows 10/11 x64 安装包及 Mac Apple 芯片 DMG；离线完整程序包升级 | 新装无客户预设或示例，空库自动引导，单水平/多水平分别建成首个项目并首次显示对应简短教程；在 A 版本建立资料后升级 B，原资料、自选路径、附件、报告及引导状态保持；未知结构拒绝写入，取消和失败回到一致状态。 |
| 第二轮 启动在线更新 | HTTPS 更新入口，可信元数据，分平台检查与下载，独立更新助手，进入业务前安装，手动检查入口 | 无新版快速启动；断网继续使用；损坏包、错误平台、磁盘不足及各阶段强制中断均有明确恢复结果；原资料保持。 |
| 第三轮 统一正式发布 | 同提交多平台构建、网页维护部署、客户端上架、下载页、发布回执及小范围试用渠道 | 实际走完同版本网页与桌面发布，并覆盖网页失败、上传失败、元数据发布失败和跨多个版本升级；已新增资料的客户端不会被旧备份覆盖。 |

必要实机环境为 Windows 10、Windows 11 和 Apple 芯片 Mac；Mac 使用对应最低支持系统验证。还需检查普通系统用户、中文和空格路径、多开、浏览器备用入口、卸载后重装、进程占用、下载中断及完整备份恢复。源码测试与本机逻辑检查不能替代签名后的安装包验收。

首次使用专项需覆盖：安装产物无预置客户或示例项目；内置参考目录不抑制空库引导；两种方法均能从空库走完实际设置；未保存的选择不写业务资料；教程简短且与最终方法匹配，包括首次选单水平但保存前改为多水平；稍后、继续、完成及数据库切换正确保留进度；升级不再次写入示例、不重置客户选择或引导状态，旧库缺少新增教程状态也不会被当成全新用户。可复用 `tests/onboarding_service_smoke_test.py`、`tests/onboarding_ui_smoke_test.py` 以及快捷建项和三方法关联检查，再补两平台真实首次启动验收。

以当前功能版为起点，还需在 Windows 和 Mac 实包验证：Ct四种条件及等值和小数边界、黄色提醒与原失控红色优先、原统计和历史来源冻结、配置和检测导出字段、图表/PNG/PDF及完整恢复；即时法转入 L-J 后整组草稿保留、目标批次重新核对、原即时记录保持及重复请求保护。复用本轮 `ct_alert_*`、`ct_chart_report_smoke_test`、`instant_daily_transfer_smoke_test`、`instant_daily_transfer_ui_smoke_test` 等对应验证。两平台离线帮助包含18节主文、目录和5张原图，PDF中Ct小数保留当前精度。

软件下载专项验证未发布时没有假链接或假版本、发布记录完整且地址有效时才显示下载、错误平台和无效地址不产生下载链接、帮助入口与返回保留当前资料及未保存草稿、打包资源包含下载清单和新页面模块。

第一轮可以开始处理公共基础，同时分别建立 Windows 与 Mac 构建环境；第三轮成功后再优化差量下载。对外上线前落实域名和 HTTPS、平台签名及 Mac 公证所需账号、签名密钥的保管和恢复方式、各目标实机环境。费用和账号操作另按实际选择处理。
