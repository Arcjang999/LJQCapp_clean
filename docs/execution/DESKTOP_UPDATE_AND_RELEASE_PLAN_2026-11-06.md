## 2 用户安装和更新体验

客户首次从网页版“帮助 → 软件下载”获取 Windows 10/11 64位或 Mac Apple 芯片的固定 1.00 基础包。更新接入补丁发布后，同页明确提供其一次性入口和说明；客户运行接入补丁后拉取最新累计更新。安装后的桌面软件隐藏软件下载页，后续只提供本机更新状态和“检查更新”。客户端根据包内构建目标选择补丁，不能依赖浏览器识别系统。

| 用户电脑 | 首次安装包 | 后续更新目标 |
| --- | --- | --- |
| Windows 10/11 64位 | 现有 1.0.0/build2026110606 Setup，原字节固定 | `windows-x86_64` 累计程序补丁 |

开发改造方案保存在本文件 `docs/execution/DESKTOP_UPDATE_AND_RELEASE_PLAN_2026-11-06.md`，通过项目交接文档和 `AGENTS.md` 索引。客户下载页只呈现平台、正式版本、发布日期、包大小和下载入口。

`resources/software_downloads.json` 保存网页的基础安装包展示信息，当前固定 build2026110606 两份原文件；普通补丁发布不修改这些记录，只有明确授权刷新基础包才变更。`services/software_download_service.py` 校验记录，`ui/software_downloads.py` 展示。未发布的平台显示“安装包准备中”；清单缺失或损坏仍能返回主页，单条坏记录不影响另一平台。一次性接入组件和补丁元数据须独立建模，不能用它们冒充此清单中的 Setup/DMG。

### 空库首次设置与新手教程

正式安装包首次使用时没有预置项目、批次、检测结果或报告，也不预填客户的实验室名称、人员、仪器、试剂批号、质控品批号及靶值。内置的标准、单位及产品目录继续作为客户选用的参考资料，不能代替客户的实际登记和确认。已有本机或云端资料继续保留，空库要求只适用于全新使用。

首次流程为：

`打开空白业务库 → 选择单水平或多水平 → 登记本单位实际资料 → 建立首个检验项目和批次 → 对应工作台显示简短教程`

方法选择不给默认项，使用两个简短选项：

| 选项 | 用途说明 | 后续引导 |
| --- | --- | --- |
| 单水平（L-J） | 按一个浓度水平的均值和 SD 建立 L-J 图，观察连续结果的波动和偏移。 | 设置一个水平，按客户选择的建靶或已确认参数方式完成首个检验项目。 |
| 多水平法 | 各浓度水平使用各自的均值和 SD，再结合当次及连续结果按所启用的规则综合判读。 | 选择实际水平数，为各水平选择产品、原厂批号和参数，再建立首个检验项目。 |

此选择只决定本次教程与首个检验项目的草稿预填。客户可在保存前调整，后续也可使用另一方法；项目内各检验项目仍可分别选择方法。选择教程本身不创建项目、不保存批次、不代替质量核对或参数确认。即时法仍沿现有单水平入口按需选择，首次选择页只呈现用户要求的单水平和多水平两个选项。

资料准备复用已有“实验室信息 → 仪器试剂管理 → 新建项目”入口及保存校验，并根据所选方法带入首项草稿。必需资料由客户填写；缺项时提示对应字段和处理入口。提示只写当前要做的事，每处以一句为主，教程保持简短。

第一次进入对应工作台时，可使用以下教程提纲，并以实际按钮名称校对最终文案：

| 方法 | 简短教程提纲 |
| --- | --- |
| 单水平（L-J） | 核对当前项目和批号；填写检测时间、检测人和一个质控值并保存；查看质控图和判读，需要时生成报告。 |
| 多水平法 | 核对各水平产品和批号；同一次检测填写全部水平结果并保存；查看整次检测判读和各水平质控图，需要时生成报告。 |

复用现有空业务库自动弹出的首次引导，增加方法选择和按方法带入草稿。引导进度绑定数据库，保留“稍后再做”、继续和手动入口。教程按数据库及方法分别保存已查看状态，查看单水平教程不会同时标记多水平教程；正常升级保留这些状态。已有业务库升级时沿用不强行启动首次设置的约定，客户可从帮助手动查看教程。

旧引导的步骤、跳过和完成状态继续有效；接续旧的未完成进度时保留原步骤，在需要按方法建立项目时再补选方法。现有引导状态只规范化 `version/step/status`，方法选择和各方法教程状态使用独立设置键保存，避免扩展字段被旧规范化函数丢弃。切换数据库后使用该库自己的引导状态，不用安装次数、版本号或教程状态缺失代替首次使用判断。教程以最终保存并实际进入的工作台方法为准，不能一直沿用最初选择。

现有 `services/demo_data_service.py` 的旧 full/basic 示例及“写入演示数据.bat”不会用于新的客户发行包；首次启动、覆盖安装和更新均不能向客户库写入旧示例或恢复仓库试用快照。此处沿用用户最新的空库引导要求，不实施此前讨论的 HIV RNA 示例或独立演示入口。

现有 06 基础包先通过独立的一次性接入补丁建立更新入口，不重新制作基础安装包。首次接入核对实际启动入口与原保存位置；后续检查和程序补丁切换由稳定启动器及独立助手完成。

计划中的启动检查先读取本机版本，再以短超时取得小型服务器清单；有可用新版时显示版本、更新内容和“下载更新／稍后”。下载可在后台进行，安装必须在用户保存工作并正常退出后。应用已经进入业务录入时不切换正在运行的程序。已有待安装包也须重新核验清单有效期、文件完整性及安装条件，不能因存在缓存文件就直接执行。

断网、版本服务超时或元数据过期时，继续使用本机已安装且与当前数据兼容的版本。损坏的包、错误系统或架构、签名无效、磁盘不足均取消本次升级。客户端不自动绕过系统安装保护。

## 3 程序与资料分别保存

| 平台 | 程序位置建议 | 固定配置及默认资料位置 |
| --- | --- | --- |
| Windows | `%LOCALAPPDATA%\Programs\LJQCApp\`，包含稳定启动器、更新助手及 `versions\<build>\` | `%LOCALAPPDATA%\LJQCApp\`，分别存放 `config`、`data`、`backups`、`updates`、`logs` |
| Mac | `/Applications/LJQCApp.app` 或 `~/Applications/LJQCApp.app` | `~/Library/Application Support/LJQCApp/`；日志可放 `~/Library/Logs/LJQCApp/` |
| 网页服务器 | 程序继续使用 `/opt/ljqcapp` | 继续使用 `/var/lib/ljqc`，沿用服务器现有数据库、附件和备份 |

用户已通过系统设置选择的数据库位置继续生效，附件仍跟随实际数据库路径。安装、程序升级和普通卸载保留固定资料目录及自选位置。独立数据目录是默认设计，不增加实验室账号或多租户。

首次接入按确定的旧软件文件夹定位原配置，避免从多个副本中猜选数据库：

1. 关闭旧窗口、备用浏览器服务及维护进程，取得安装和实际数据库路径对应的锁。
2. 有有效自选路径时，将该指针写入稳定配置，继续使用原库；原库缺失或配置损坏时提示选择原软件文件夹或核对保存位置，保留原资料。
3. 原来使用包内默认库时，把数据库、登记附件和报告一起复制至稳定资料目录，核对后最后写配置。原位置先保留，使用完整快照协调 SQLite 的 WAL 等文件。
4. 配置、候选目录或目标已有资料存在冲突时停止切换，不能静默改用新空库，也不能仅移动一个 `.db` 文件。

## 4 数据兼容和升级失败处理

这是接入自动更新前的必要基础。当前最小兼容门槛会在旧初始化器可能重建核心表之前拒绝未知列、未知迁移登记和不支持的格式版本；这层防线已实现，完整迁移协调尚未实现。更新器仍不能让旧程序直接接触未知新版结构。

增加明确的数据结构版本、最低兼容程序版本和完整迁移登记，在自动旧库迁移、`init_db()` 及任何业务写连接之前进行只读检查。首次接入只有经识别和验证的基线才能登记为受支持结构；未知结构保留原状并停止自动升级。调整“列不完全相同就重建”的判断，防止把未来结构当成旧格式处理。

切换过程采用持久阶段日志：

`已下载并验证 → 已取得维护锁 → 已封存原资料 → 候选迁移与验证通过 → 程序和资料已切换 → 启动验证通过 → 允许业务写入`

更新器从最终快照到放行写入一直协调维护状态。正常关闭时先结束在途写入、等待连接和 Qt 子进程释放；无法安全退出则延期更新。现有 `taskkill /F` 不作为常规升级动作。单实例和资料锁应覆盖桌面窗口、备用浏览器入口、维护工具及更新器。

先由旧版本生成完整备份，或使用不初始化数据库的原始封存，再让新版在候选库上验证迁移。当前公开备份 API 会调用 `init_db()`，不能先让新版通过“备份”接触在用库。现有完整备份、附件清单、哈希核对和恢复前保护可以复用；多处显式提交与跨文件操作仍需独立的断电恢复设计。

候选库通过完整性、外键、原记录和字段、附件哈希、历史报告字节及业务验证后，才切换正式资料。候选资料在目标文件系统内暂存，配置和程序入口采用可恢复的切换方式；程序、数据库及附件的多文件变化由阶段日志协调。

| 失败时点 | 恢复规则 |
| --- | --- |
| 下载安装前 | 保留现有程序和资料，重试下载。 |
| 候选升级未通过 | 保持原程序和原资料，保留失败日志与候选资料供诊断。 |
| 已切换但尚未允许新业务写入 | 根据阶段日志恢复升级前相互匹配的程序、库、附件及配置，验证后再启动。 |
| 新版已保存新结果、报告或附件 | 保留最新资料；只有经验证兼容时才退回旧程序。不能自动恢复升级前备份覆盖新增资料，应发布修复版或执行经验证的逆向迁移。 |

## 5 平台安装和更新实现

Windows 保留现有 Qt 窗口、本机服务和普通用户基础 Setup。现有快捷方式直接指向 `versions/<PayloadId>`，没有 `current.json` 或稳定 bootstrap。一次性接入补丁先安装独立助手和稳定入口，准确更新原快捷方式，验证后交给新入口启动；不能让助手依赖正在替换的 Qt 目录。日常更新正常退出窗口及服务后，将已验证程序归档展开至新版本目录，核对完整清单，最后原子切换入口指针。原基础 Setup 不改，不要求客户每次重新运行安装器。定义助手自身的最低版本和受信任升级路径，保留用户取消和系统保护，不强制结束程序。

Mac 已有 `.app` 与 DMG 配方，原 DMG 固定为基础包。一次性接入组件须建立真实生效的稳定启动入口，接续应用程序目录和 Dock 等原入口；更新后不能仍启动无更新器的旧应用。日常补丁交付完整 `.app` 归档，协调主窗口、本机服务及 QtWebEngine 全部退出后，由应用包外的独立助手切换；保持权限、符号链接、签名和系统下载来源信息。当前未 Developer ID 签名及公证，正式自动切换须在该分发条件下完成平台验证，不能宣称静默更新已实现。可评估 Sparkle 或独立助手，但须以本项目冻结应用实包验证；更新签名不能替代 Apple 应用签名、公证，不能关闭 Gatekeeper。[Sparkle 官方说明](https://sparkle-project.org/documentation/)、[Apple Developer ID](https://developer.apple.com/developer-id/)

对外 Mac 发行使用 Developer ID 签名、所需 hardened runtime 权限、公证及票据装订，并验证 Gatekeeper 的正常打开体验。更新包签名与 Apple 应用签名分别管理。[Apple 发行说明](https://developer.apple.com/developer-id/)

Mac 构建固定为 arm64，Python、Qt 和全部原生依赖均需具备该架构。最低 macOS 版本在选定依赖并完成目标系统验证后写入清单。[PyInstaller 架构说明](https://pyinstaller.org/en/stable/feature-notes.html#macos-multi-arch-support)

当前配方同时收集源码资源和冻结模块，逐个覆盖 `.py` 可能形成混合版本。第一版补丁切换完整程序目录或整个 `.app`，下载量可能接近安装包；“固定基础包”不等于第一版已有小体积差量。以后从完整的两平台构建产物生成文件或二进制差量，绑定精确起止摘要，重建后核对完整目标；差量不适用时改取同版完整程序补丁，不自动改用新 Setup/DMG 或替换基础包。

发行包只带程序、内置目录、帮助和必要运行环境。构建检查排除在用数据库、演示数据库或试用快照、保存位置配置、业务附件、备份、日志和签名私钥；客户数据库在首次使用时初始化为空白业务库。解压前验证大小与路径边界，暂存完成后复核完整目标；Mac 应用内必要的符号链接需保持在受验证的包范围内。

## 6 服务器版本核验与客户端下载

`release.json` 是每次构建的唯一版本源；`build_info.json` 记录其实际提交、发行输入摘要和目标。网页显示“网页版”，桌面显示“桌面版”，分别标明功能版本和构建号。两种发行使用各自已完成验证的构建，不把网页最近一次部署号用作桌面最新版本，也不要求为了仅改网页下载说明而强制所有桌面安装。

服务器无须连接客户数据库，也无须主动向每台电脑推送文件。发布程序先核对构建回执、目标、干净源码、文件长度和 SHA-256，上传并复核不可变补丁，最后发布小型签名更新清单；已接入更新组件的客户端每次启动或手动检查时拉取它，在本机比较版本和兼容条件。“推送新版”就是发布新的清单，客户允许更新后才下载适用的累计程序补丁。断网或无适用补丁时继续当前兼容版本，不阻塞日常使用。

现有服务器使用 `https://159.75.243.120/`，安装包位于 `/downloads/releases/<version>/<build>/`，磁盘目录独立于 `/var/lib/ljqc`。此静态下载及证书续期已经配置，具体现场验证以本轮回执为准。以下 `/updates/` 路径是后续设计，尚未创建或宣称可用：

| 信息 | 计划地址 | 缓存与用途 |
| --- | --- | --- |
| 网页发布信息 | `/updates/web/version-info.json` | 仅展示网页功能版本、构建号及部署时间，不参与桌面更新判断。 |
| 桌面公开版本信息 | `/updates/desktop/dev/version-info.json` | 可先发布已验收平台版本、包大小和 SHA-256，供人工核对；须明确 `automatic_update_available: false`。 |
| Windows 更新入口 | `/updates/desktop/dev/windows-x86_64/latest.json` | 小型、带签名、短期有效；重新验证缓存后读取，原子替换。 |
| Mac 更新入口 | `/updates/desktop/dev/macos-arm64/latest.json` | 与 Windows 分开，不能把一种架构的包交给另一端。 |
| 安装包 | `/downloads/releases/<version>/<build>/<immutable-file>` | 文件发布后不覆盖，允许长缓存与断点下载；撤下错误入口也不把客户端自动降级。 |
| 一次性接入组件 | `/downloads/update-bootstrap/<updater-version>/<target>/<immutable-file>` | 计划路径；独立版本、长度及哈希，可供首次人工接入，不替换基础安装包。 |
| 日常程序补丁 | `/downloads/patches/<base-release>/<version>/<build>/<target>/<immutable-file>` | 计划路径；按平台保存累计完整程序归档，后续可增加绑定精确来源的差量。 |

当前开发版使用 `dev` 渠道。以后增加 `stable` 时，由发布者明确晋级，客户端不能在渠道间自动跳转。未接入受信任更新器之前，普通版本信息不叫可自动安装的更新清单，现有 `software_downloads.json` 继续只服务网页下载展示。

计划中的签名清单至少包含：

| 字段 | 校验目的 |
| --- | --- |
| 清单格式、产品、`edition=desktop`、渠道、目标系统及架构 | 防止误读网页信息、其他应用、错误渠道或错误平台。 |
| 功能版本、整数构建号、递增清单序号、发布日期、过期时间 | 功能版本用于显示；同渠道同目标用构建号判断是否更新，拒绝旧清单回放、相同序号内容变化及过期元数据。 |
| 来源提交、源码摘要、包 URL、长度、SHA-256 | 将用户看到的发行信息与精确包字节绑定；缺字段不能进入下载/安装状态。 |
| 基础发行标识、补丁类型、支持的起始版本/摘要、完整目标清单及可选前置阶段 | 固定 1.00 基础包，累计补丁覆盖承诺的起始版本；不能混用其他基础包，差量须严格匹配来源并核验重建结果。 |
| 最低系统、最低更新助手版本、数据格式声明、受支持原结构及迁移要求 | 当前未知结构不自动升级；需要迁移的版本须先具备完整的候选迁移与恢复协调。不能只比较一个格式整数。 |
| 变更摘要、`key_id` 与签名 | 先用软件内置公钥验签，再解析和展示可操作更新。 |

签名规范固定为经测试的 UTF-8 元数据字节及签名封装；更改任意受签内容必须重签。客户端保留已接受的最高清单序号及已安装构建号，验证签名、有效期、版本次序和全部约束后，才接受下载地址。HTTPS 保护传输，SHA-256 证明下载与清单一致；同一服务器可同时替换包和无签名哈希，因此它们不能代替发行签名。私钥放受控发布环境，不放下载服务器、源码或安装包；客户端只内置公钥，密钥轮换须预先设计。此为最小设计，未声称已经符合完整 TUF。[TUF 元数据角色](https://updateframework.com/docs/metadata/)、[TUF 客户端回退与过期校验](https://theupdateframework.github.io/specification/latest/)

客户端下载写入固定资料根的 `updates/<release-id>/<artifact>.part`，不直接写安装目录。只允许预定 HTTPS 发行来源，限制重定向、清单/包长度、超时、磁盘空间及解包路径；恢复下载需匹配同一签名清单、URL 和强验证器，检查 `206 Content-Range`。若服务器返回 `200`，重新开始整包，不能把整包追加到旧片段。下载结束后重算完整长度及 SHA-256，必要时验证归档签名，成功才在同一文件系统原子改名为已验证候选，并记录持久阶段日志。`ETag` 仅帮助续传，不替代最终哈希和签名。[HTTP Range 与 If-Range 规范](https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests)

**补丁切换门槛：** 用户确认并保存工作 → 正常关闭主窗口及服务 → 确认桌面锁、服务锁和目标资料维护锁均释放/取得 → 旧程序完整备份或只读原始封存 → 已验证候选及兼容检查 → 平台程序切换 → 新版启动验证。现有桌面锁和服务锁是基础，稳定入口、更新助手之间的独立维护锁及断电恢复日志尚须实现。超时延期，不强制结束；切换失败保留原程序和当前资料。新版已经写入业务后，不自动恢复升级前备份覆盖新记录、报告或附件。

现有 build06 基础包和此前包都不会因为服务器出现清单就自动更新。按固定基础包的新约定，需另发并运行一次性接入补丁，验证信任公钥、实际启动入口和资料位置后才具备启动检查能力。06 的端别界面调整不等于已包含更新器；现有基础包文件保持不变。

## 7 网页和桌面的发布次序

发布依次完成：

1. 对本轮需要更新的发行端建立准确版本和提交；桌面两个目标从同一确定源码分别构建并验收补丁，网页记录自己的部署版本。日常发行不制作替换基础包；基础包刷新须有项目负责人明确指令。
2. 上传到不可变版本目录，复核包和签名，保留正式版本入口指向原版本。
3. 网页端预告短暂维护，让使用者保存当前填写内容并退出；维护期间阻止新增业务写入，备份服务器当时资料，部署本轮网页的确定提交。通过服务、真实页面和资料核对后恢复使用。
4. 所需平台补丁均通过后，最后原子发布该渠道的签名更新元数据。网页基础包下载记录保持原 1.00；若展示最新程序或补丁信息，引用同一补丁发布索引并明确与基础包区别。只部署网页的改动不修改桌面清单。
5. 保存每一阶段的回执及已发布目标。网页部署失败时不发布客户端入口；网页成功而更新入口发布失败时，按日志补发。

一轮包含网页和桌面功能变更时，记录两者对应来源及共同发布说明；它们的生效时间和已安装状态仍独立。网页部署完成后生效，桌面在客户联网并确认完成升级后生效。已升级的客户端不受服务器入口退回影响；错误版本应撤下更新入口并发布更高构建号修复，遵守当前数据兼容范围。

### GitHub 到自有服务器自动发布

用户已提出后续构建成功后直接从 GitHub 传到服务器。推荐增加独立发布任务，省去先下载本机再上传的中转；**当前仍是计划，尚未配置部署身份、部署凭据或自动上传任务**，本轮生成的安装包身份不因此改变。

一次性接线使用专用、低权限的服务器部署身份：只向本轮 staging 目录上传，发布动作由受限的固定接收/晋级命令处理；不能访问 `/var/lib/ljqc`、业务配置和备份，也不授予任意 root shell。专用凭据放 GitHub 的部署 environment secrets，环境限制可信发布分支；服务器主机公钥从可信控制台核对后固定，禁止关闭主机校验。不得上传 root 私钥、个人通用 SSH 私钥或更新签名私钥到服务器/仓库；签名身份与上传身份分开。日志只记录版本、文件名、哈希和阶段结果，凭据不进命令回显、构建附件或错误正文。GitHub 的环境保护规则与 environment secrets 可用于约束这类发布任务。[GitHub 环境说明](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)、[GitHub Secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)

计划流程为：

1. 将现有候选 Setup/DMG 工作流改造为普通发布默认产出两平台补丁；明确的基础包发行任务另行制作和晋级 Setup/DMG。等待同一 release 的 Windows、Mac 构建及实包检查全部成功，取得同一次确定提交的两份补丁和回执；逐目标验证基础发行、版本、构建号、共同来源摘要及各自长度、SHA-256。一端失败、缺包或来源不一致时不发布，不能从另一次运行拼凑“最新包”。
2. 从 GitHub runner 直接上传到服务器 staging，服务端重新验证文件及签名；以 release 标识隔离并发上传，旧任务晚完成也不能把渠道指针退回旧构建。接收过程不重启业务服务、不连接客户数据库。
3. 整组核验通过后，将两份补丁晋级到不可变补丁目录；同名旧文件若哈希不同则拒绝覆盖，保留上一版。验证真实 HTTPS 下载响应后，最后原子切换单一的补丁渠道索引，两平台清单共同引用该 release；读取方须校验索引指定的整组清单，不能把逐个覆盖多个文件当作整体原子切换。网页基础包记录继续固定 1.00；尚未接入签名更新器时只公布人工可核对信息，不能伪造可自动安装的清单。
4. 记录 run ID、完整提交、产物哈希、已发布 release 及结果，不记录客户资料。失败保留 staging 及诊断，继续提供上一版下载。

客户始终从自有服务器的 HTTPS 地址下载，不使用 GitHub Actions 短期 artifact 地址；Actions 附件受保留期限和访问权限约束，只作为构建交付的中间产物。[GitHub 附件下载说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)

网页程序部署保留独立步骤和版本回执。即使随后将其接入 CI，也必须针对服务器当时的资料核对兼容性、验证原始封存及完整双备份，再切换已验收源码；不能借安装包自动上传顺便恢复旧库、替换资料位置或覆盖现有报告和附件。

以当前功能版为起点，还需在 Windows 和 Mac 实包验证：Ct四种条件及等值和小数边界、黄色提醒与原失控红色优先、原统计和历史来源冻结、配置和检测导出字段、图表/PNG/PDF及完整恢复；即时法转入 L-J 后整组草稿保留、目标批次重新核对、原即时记录保持及重复请求保护。复用本轮 `ct_alert_*`、`ct_chart_report_smoke_test`、`instant_daily_transfer_smoke_test`、`instant_daily_transfer_ui_smoke_test` 等对应验证。两平台离线帮助包含18节主文、目录和5张原图，PDF中Ct小数保留当前精度。

软件下载专项验证未发布时没有假链接或假版本、发布记录完整且地址有效才显示下载、错误平台/无效地址不产生链接；网页入口与返回保留当前资料及草稿，桌面完全不显示软件下载，旧内部路由不能重新打开它。桌面未来的“检查更新”应独立于网页下载展示清单，版本标签与实际包内元数据一致。

现阶段可维护实际下载包、公开版本/哈希信息、端别标识及独立渠道设计；这不需要开启客户数据访问。在线检查、受信任签名下载、安装接管和完整迁移协调仍需后续开发及实包验收。IP HTTPS 已有配置与自动续期，仍须监测续期结果；代码签名、公证及更新签名私钥分别管理，费用和账号操作另按实际选择处理。
